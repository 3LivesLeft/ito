# v0.3 VM and hardware acceptance tests (prepared, not run)

**Status:** prepared in M1.2 (19 Nov 2026). **None of these has been run.** They are **public
release blockers** (roadmap RG-13 and RG-14) and need a VM host and a spare Pi; the cloud sessions
used so far have no virtualisation. They replace mocks and
source reading with real Home Assistant OS, a real Supervisor and the real app store and
Marketplace. Until a test here passes, the matching claim stays *unverified* in the threat model,
ADR 0006 and the review handover. Results go in a new `docs/testing/v0.3-vm-results.md`, with no
household identifiers (CLAUDE.md rule 15).

**Numbering.** IN-1 to IN-11 follow the journey in [getting started](../getting-started.md). If the
implementation plan numbers them differently, the plan's numbering wins and this table is
renumbered to match.

## Ground rules

- **Isolated VMs only.** Never the maintainer's Raspberry Pi or any Home Assistant someone relies on.
- **No live Reticulum networks** (CLAUDE.md rule 6). Peers, when a test needs one, are a second
  MeshBeacon or `rnsd` on the same isolated VM network. The VMs do need internet access to reach
  GitHub, GHCR and the Home Assistant update servers, because that is what installation is.
- **Shell access only for checking.** Tests use the user interface, as a new user would. A few
  checks read state from the host (HAOS developer SSH on port 22222, enabled only on the test VM).
  None of them changes anything.
- **Record versions:** HAOS, Supervisor (and its channel), Core, the app and the integration.

## Host-side commands

From the HAOS developer console of the test VM:

```sh
docker ps --format '{{.Names}}' | grep meshbeacon          # e.g. addon_ce27fbb5_meshbeacon
C=addon_ce27fbb5_meshbeacon
# The test VM's own Supervisor token as the canary, without putting it on any command line:
docker exec "$C" sh -c 'umask 077; cp /run/s6/container_environment/SUPERVISOR_TOKEN /tmp/c2; \
  chown meshbeacon /tmp/c2'
# The observer runs beside the app, not inside it: the app's AppArmor profile refuses even a
# privileged process inside the container ptrace access (seen in CI). It reads the canary itself.
IMG=$(docker inspect -f '{{.Config.Image}}' "$C")
docker run --rm -i --privileged --pid=container:"$C" --network none --security-opt apparmor=unconfined \
  --entrypoint python3 "$IMG" -I - observer @auto < relay_probe.py                 # the truth
docker exec -u meshbeacon -i "$C" python3 -I - attacker @/tmp/c2 < relay_probe.py  # Reticulum's view
docker exec "$C" stat -c '%a %U %G %n' /run/meshbeacon /run/meshbeacon/discovery.sock
journalctl -k --no-pager | grep -E 'apparmor="DENIED".*meshbeacon'
```

Copy `tools/acceptance/relay_probe.py` onto the VM first, for example by pasting it into the
console. Each view prints one JSON line and no secret; `@FILE` deletes the copy it read.
**Isolated** means: observer `core_non_dumpable: true`, every other observer key `false` except
`core_holds_link` (`true` in socket mode only); attacker: every key `false`.
