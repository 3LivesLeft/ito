# ADR 0025: Rename the product to ito; keep the `meshbeacon` identifiers

**Status:** Accepted (maintainer, 21 November 2026: PR #12, and the decisions on artwork, scope
and entity IDs recorded below). **Supersedes:** the MeshBeacon name and lighthouse identity in
[branding](../branding.md) (18 Nov 2026), and `mdi:lighthouse-on` wherever it is named, including
the proposed ADR 0013. **Related:** ADR 0006 (discovery), ADR 0007 (panel),
[naming research](../research/naming.md).

## Context

The project was called MeshBeacon, which another, unrelated project also uses (naming research).
The maintainer chose a new name, **ito** (always lower case; tagline *The internet, reimagined.*),
and proposed provisional thread-and-earth artwork in PR #12. That PR was written against v0.2.
Since then the product has gained a sidebar panel, LXMF messaging and a full brand pipeline, all
named MeshBeacon, and installations exist whose data, entities and identities must survive.

## Decision

1. **Everything a user reads says ito.** The app and integration names, config flow, repairs,
   option texts, the panel and its Messages tab, app log messages, the automatic LXMF reply, user
   documentation and README. `project.yaml` holds the name; `tests/unit/test_project_identifiers.py`
   checks every place that must follow it.
2. **Identifiers do not change.** App slug, integration domain and Supervisor discovery service
   (`meshbeacon`), Python package and data paths, config entry and entity **unique** IDs, and the
   Reticulum and LXMF identities. Changing the slug would move the app's data folder; changing the
   domain would orphan every config entry. Wire-level names nobody reads (the status API's TLS
   certificate name and `Server` header, the comment in the generated Reticulum configuration)
   and code identifiers (class names, the font's private family name) also stay.
3. **The device is called ito, so new entity IDs start with `ito_`.** Home Assistant derives a new
   entity ID from the device name. Existing entities keep their `meshbeacon_` IDs, because Home
   Assistant never renames a registered entity, so automations, dashboards and history are
   unaffected. New installations get `sensor.ito_status` and similar. The example dashboard uses
   `ito_` and tells earlier users how to switch it. The panel looks entities up in the registry and
   works with either.
4. **Provisional ito artwork replaces the lighthouse everywhere it is shown.** That covers the app's
   icon and logo, the integration's brand images, the panel's mark and the README. The masters in
   `branding/src/` are a vector interpretation of PR #12's emblem and favicon, and every variant
   is regenerated by `tools/brand/build.py`. The panel's accent becomes deep green `#284C40`
   (light) and sage `#A6C9B2` (dark). Status and chart colours are unchanged, and WCAG 2.2 AA is
   still checked automatically. The sidebar icon is `mdi:earth`.
5. **History is not rewritten.** ADRs, research, test records and earlier changelog entries keep
   the name they were written under.

## Consequences

- An update in place is enough. There is no migration, the user does nothing, and nothing is
  reinstalled.
- Contacts who receive an automatic reply see "ito received your message" from the same LXMF
  address as before.
- A user with both an old and a new installation sees `meshbeacon_` and `ito_` entity IDs side by
  side. That is expected and documented.
