# ADR 0021: v0.3 is a distribution release; messaging follows behind security gates

- **Status:** **Accepted** (maintainer, 19 November 2026)
- **Date:** 19 November 2026
- **Deciders:** MeshBeacon maintainer
- **Evidence:** [Roadmap](../roadmap.md), [forward-compatibility review](../research/long-term-direction.md)
- **Supersedes:** the v0.3 scope in the roadmap of 18–19 November 2026 (LXMF send/receive, HA
  `notify` platform, interoperability testing and optional propagation node as one v0.3 release).
  **Amends:** [ADR 0001](0001-networking-foundation.md) ("from v0.3, LXMF" now means the v0.3
  messaging milestone). The superseded scope is kept in the roadmap's history section.

## Context

The earlier v0.3 plan combined first publication with messaging. Publishing is gated on release
gates RG-1 to RG-12 and makes the name, slug and data layout effectively permanent (ADR 0003).
Messaging needs an authorised path from Home Assistant to MeshBeacon. The maintainer has
determined that the default service-call permissions of Home Assistant's `notify` platform do not
meet MeshBeacon's messaging authorisation requirements: any caller able to use the service could
send messages under the user's LXMF identity **[Assumption — to be verified against the HA
release in use when the messaging ADR is written]**.

## Decision

1. **v0.3.0 is an installation and distribution release** through Home Assistant's native app
   installation path (an app repository added from the App store, with a one-click My Home
   Assistant link), and any further catalogue the maintainer names (Q-43). It adds no
   application features. It requires all Tier B release gates and explicit approval to publish.
2. **Secure LXMF messaging is a subsequent v0.3 milestone**, released only when its gates are met
   (roadmap "v0.3 messaging gates"), including the Home Assistant / Supervisor security
   capabilities that authorisation needs.
3. **The HA `notify` platform is removed from the committed v0.3 scope.** It may return only with
   an authorisation design that meets the messaging requirements, in its own ADR.
4. **The optional LXMF propagation node moves to proposed v0.5** (community services), where it is
   designed as a public service under [ADR 0019](0019-opt-in-publication.md) and
   [ADR 0020](0020-public-service-isolation.md).
5. **RNode/LoRa hardware support remains an explicit future capability**, unscheduled, needing an
   ADR for device access (hard rule 4).
6. **v1.0 is an unscheduled stability milestone**, defined by its criteria, not by a date or a
   position after a particular version.

## Consequences

- No write path from Home Assistant exists in v0.3.0; ADR 0006 stays read-only.
- Interoperability testing with other LXMF clients moves with messaging to the messaging milestone.
- The naming decision (Q-41) must be taken before v0.3.0 publishes anything.

## Amendments

- **19 November 2026 (later the same day):** decision 1 made precise after verification against
  Home Assistant 2026.11.2 ([v0.3 distribution](../research/v0.3-distribution.md)). v0.3.0 uses
  **two** native mechanisms: the **App store** (Supervisor) installs the backend app; the
  **Marketplace** (Core integration `marketplace`) installs the integration. "Any further
  catalogue (Q-43)" is replaced by this; Q-43 and Q-45 are resolved.
- **Process isolation:** the specific process or IPC model is deferred until security review and
  Raspberry Pi memory measurements are available ([ADR 0020](0020-public-service-isolation.md)).

## Review triggers

Home Assistant gaining per-service or per-user authorisation suitable for messaging; any proposal to
bundle features into v0.3.0.
