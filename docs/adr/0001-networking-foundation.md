# ADR 0001: Build on the Reticulum reference implementation directly, not on Rathole

- **Status:** Proposed (awaiting maintainer review)
- **Date:** 18 November 2026
- **Deciders:** MeshBeacon maintainer
- **Evidence:** [Feasibility study §2](../research/feasibility.md#2-reticulum-versus-rathole-research-item-1),
  [Licensing §3.3](../research/licensing.md#33-compatibility-conclusion)

## Context

MeshBeacon needs a Reticulum networking stack inside a Home Assistant app. The candidates were:

1. **RNS**, the Python reference implementation (`rns` on PyPI, 1.6.0 at the time of writing),
   used through its public API, configuration file and utilities.
2. **Rathole** (`ratspeak/rathole`, 1.0.0, commit `917b2ac`), a Python "transport node security
   suite" that runs RNS with packet filters, a TUI, I2P helpers and a gateway registry.
3. **rsReticulum** (Ratspeak's Rust implementation) or another non-reference implementation.

The preliminary preference in the project brief was option 1, citing maturity, monkeypatching and
maintainability concerns about Rathole. Phase 0 was asked to validate or challenge this.

Verified facts that bear on the decision:

- Rathole replaces `RNS.Transport.inbound()` and `RNS.Transport.path_request_handler()` at
  runtime and writes RNS's name-mangled private attributes (`_Reticulum__transport_enabled`,
  `_Reticulum__instance`). It declares `rns>=0.7.0` and states that this is not a tested range.
- Rathole calls itself a proof of concept, has six commits, one author and no tests.
- Rathole's defaults include HTTPS registry discovery against `registry.ratspeak.org` and enabling
  transport even in client mode.
- Rathole is GPL-3.0-or-later; combining GPL-3.0 code with Reticulum-licensed RNS is problematic
  (GPLv3 "no further restrictions").
- RNS 1.6.0 added native filtering (`[filter]`), network stamps, ingress control, blackhole
  management and fast-flap blocking — covering most of Rathole's protective purpose.
- RNS upstream is now a public mirror with no issue tracker or support, maintained by one person.
- Non-reference implementations are viewed with strong suspicion by the RNS author, and Rust
  interop with current Python RNS is unverified by us.

## Decision

MeshBeacon will **use the unmodified Reticulum reference implementation (RNS) and, from v0.3,
LXMF, as pinned PyPI dependencies**, integrating only through:

- RNS's configuration file format (generated by MeshBeacon from validated options);
- RNS's public Python API and shared-instance RPC (e.g. `get_interface_stats()`);
- RNS's own command-line utilities where useful (`rnsd`, `rnstatus -j`, `rnpath`, `rnprobe`,
  `rnid`).

MeshBeacon will **not**:

- depend on, vendor, import or copy code from Rathole;
- monkeypatch, subclass-and-replace, or write private attributes of RNS or LXMF;
- implement any part of the Reticulum or LXMF protocols itself;
- adopt a non-reference implementation before v1.0.

Protective features (rate limiting, filtering, blackholing) will use RNS's native mechanisms.

## Consequences

**Positive**

- Upgrades are bounded by RNS's public interfaces; failures will be loud (startup/config errors)
  rather than silent behavioural drift.
- Clean licence position (no GPL-3.0 code in the combined work).
- Credibility with the Reticulum community: MeshBeacon is clearly an *application* of the
  reference implementation, not a fork or reimplementation.
- Privacy defaults are under MeshBeacon's control.

**Negative / accepted**

- Features Rathole offers (heuristic anomaly detection, reputation scoring, TUI, registry) are not
  available unless MeshBeacon builds them on public APIs or RNS adds them.
- MeshBeacon still depends on a single-maintainer upstream with no public issue tracker. This risk
  is *not* reduced by this decision; it is mitigated separately (exact pinning, compatibility test
  suite per RNS release, thin integration layer — feasibility R-1).
- If RNS lacks a needed hook, MeshBeacon must live without it rather than patch internals.

## Alternatives considered

- **Depend on Rathole** — rejected for the reasons above. Its ideas (I2P gateway onboarding, alert
  presentation) may inform MeshBeacon's design; its code will not be used.
- **Fork RNS** — rejected: maintenance burden, community trust, licence obligations.
- **rsReticulum** — rejected for now: interoperability and maturity unverified; would make
  MeshBeacon's correctness depend on a second, newer implementation.

## Amendments

- **19 November 2026 — [ADR 0010](0010-v0.3-scope.md):** "from v0.3, LXMF" now means the **v0.3
  messaging milestone** that follows the v0.3.0 distribution release. The rest of this ADR is

## Review triggers

Revisit this ADR if: RNS stops publishing releases or changes licence; RNS exposes an official
packet-inspection/filter plug-in API; or a security issue in RNS goes unfixed for an extended
period.
