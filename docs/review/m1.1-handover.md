## 2. The privileged discovery relay

**Files:**
- `meshbeacon/core/meshbeacon/discovery_relay.py`
- `meshbeacon/rootfs/etc/services.d/discovery-relay/{run,finish}`
- `meshbeacon/core/meshbeacon/api.py` (`relay_request`, `Discovery._relay_request`)
- `meshbeacon/core/meshbeacon/supervisor.py` (`discovery_transport`, `setup_integration`)

**Why it exists.** Newer Supervisors give each app a Unix socket that identifies it without a
token. The socket is owned by root with mode 0600 (Supervisor `e610ca8`, `api/sockets.py:78`).
MeshBeacon's core runs unprivileged (UID 9100, architecture §4.7), so it cannot open the socket.
The relay is the only root process added. ADR 0006 amendment; threat T72.

**Claims to verify:**
1. It runs only where `SUPERVISOR_SOCKET` names a socket; otherwise the run script `exec`s
   `s6-pause`, and Python never starts.
2. It accepts connections only from the `meshbeacon` UID (`SO_PEERCRED`). Its socket is
   `/run/meshbeacon/discovery.sock`, mode 0660, in a 0750 directory, root:meshbeacon.
3. There are exactly two operations:
   - **announce** POSTs `/discovery` with service `meshbeacon` and a config rebuilt from exactly
     `host`, `port`, `token` and `cert_sha256`, each validated by regex or type;
   - **withdraw** DELETEs `/discovery/<alnum uuid>`.
   No other Supervisor path can be reached.
4. A request is at most 8 KiB, with a 5 s deadline, one connection at a time, `listen(4)`. A
   stalled, oversized or vanished client is dropped and never stops the loop. That was a bug
   found and fixed during M1.
5. Nothing is logged except fixed messages. Replies never echo request content.
6. It removes `SUPERVISOR_TOKEN` from its own environment before running.

**Questions for the reviewer:**
- Is the root process justified, or is there a supported alternative? For example, a Supervisor
  option for the socket's mode or owner, or running the whole core with a supplementary group.
- **Peer authentication:**
  - Is the `SO_PEERCRED` UID check sufficient inside the container?
  - Could another process in the container run as UID 9100? Today only the core and the
    Reticulum child do.
  - Should the check also pin the PID or executable?
- **Bind-time race:** `listen()` unlinks and rebinds the socket path. Could anything create
  `/run/meshbeacon/` first, in a race? Today only root runs at that point.
- **JSON parsing as root:** inputs are bounded, but should it parse in a stricter way?
- **Strictness of validation:** is the relay's host pattern (a DNS label: `^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$`) stricter or
  looser than what the integration accepts? The integration also requires the host to equal
  the sending app's hostname.

**Tests:**
- `tests/unit/test_discovery_relay.py` (20 tests, against a fake Supervisor socket).
- `tests/container/test_container.py`:
  - `test_discovery_over_the_supervisor_socket`: a root-owned 0600 socket. The core cannot open
    it; the relay runs as root and everything else as `meshbeacon`; no token is sent.
  - `test_without_a_socket_the_relay_is_idle`.

## 4. Denial of service and resource limits

- **Relay:** one connection at a time, 8 KiB, a 5 s deadline, and a 10 s timeout towards the
  Supervisor. **Question:** can a local client keep the single slot busy indefinitely by
  reconnecting? The deadline applies per connection. Is starving the core's announce for a few
  seconds acceptable, given that the core retries with back-off?
- **Status API:** unchanged from v0.2 (`BoundedHTTPServer`, 4 connections, deadlines; flood
  test `tests/integration/test_flood.py`).
- **Integration:** the key refresh from the Supervisor runs at most once per 5 minutes
  (unchanged); version repairs are computed per poll from the status.
- **Memory:** idle RSS is 69.2 MiB, or 71.5 MiB with the integration on. That is amd64 on the
  stand-in base; the Pi has not been measured for this branch (§14).

## 5. AppArmor enforcement and privilege separation

**Files:**
- `meshbeacon/apparmor.txt`
- `tests/unit/test_apparmor_rules.py`
- the CI container job steps "Load the AppArmor profile…" and "No unexpected AppArmor denials".

**Findings during M1.** Under enforcement, the relay's `connect()` was denied. AppArmor checks a
Unix socket by the name the *server* bound it to, and the test's fake Supervisor had bound it at
`/api/supervisor.sock`. The real Supervisor binds at `/run/os/supervisor/apps/<slug>/supervisor.sock`
inside its own container (`e610ca8`: `config.py`, `apps/app.py`). That path is already inside the
profile's `/run/{,**} rwk`; an explicit line now documents it. The fake now binds at the real
path, and CI passes under enforcement.

**Questions for the reviewer:**
- Is `/run/{,**} rwk` broader than needed now that the relay exists? Consider narrowing it to
  s6's paths, `/run/meshbeacon` and the Supervisor socket.
- Should the relay run under its own AppArmor sub-profile? (No exec, no network except
  `unix`, read-only filesystem except its socket.)
- **The CI profile is not the deployed profile.** CI loads the profile under the name
  `meshbeacon-ci`; on a real install the Supervisor loads and renames it. Is the behaviour
  identical? This needs VM confirmation (§14).
- **Capabilities:** the root step keeps `chown`, `fowner`, `dac_override`, `setuid`, `setgid`
  and `kill`. Does the relay need any of them? It needs only UID 0 to own-match the socket.

## 6. Legacy HTTP discovery and downgrade risks

**Files:**
- `api.Discovery` (TCP path)
- `supervisor.discovery_transport`
- ADR 0006 amendment
- threat model T28, T73, RR-9a

**Current behaviour:**
- **Without a socket** (Supervisor 2026.11.0 and all released versions today), the app posts
  discovery over plain HTTP on the internal network with its Supervisor token. That is
  confirmed from source.
- **Interception** by a co-installed app holding NET_RAW is **not demonstrated**. That is lab
  test W3-4; the results stay private.

**Downgrade questions:**
- **Socket and token both present:** `discovery_transport` drops the token and uses the relay
  only. Is there any way to be forced onto the TCP path while a socket exists? For example, the
  relay not yet running when the core starts: the core keeps retrying through the relay and
  does not fall back to TCP. Confirm this.
- `supervisor_api_tcp: false` is **not** set yet, because it would remove discovery entirely on
  Supervisors without sockets. **Question:** what gate should turn it on (a minimum Supervisor
  version)?
- **Messaging credentials:** none exist in M1. The rule that none may ever travel the TCP path is
  documented (D7) but enforced only by design, not by a test. Should a test assert that the TCP
  path's payload keys are exactly the four status fields? `announce` builds them, and the relay
  enforces it on the socket path.

- `custom_components/meshbeacon/__init__.py` (`async_migrate_entry`)
- `config_flow.py`, `entity.py`, `panel.py`, `coordinator.py`

**Claims:**
- **Version 1 → 2:** `node_key` and `app_slug` are both set to the old unique ID, so entity
  unique IDs, entity IDs and history do not change.

- **After a future move,** only `app_slug` changes. Migration of existing installations is M6,

- The entry's `unique_id` remains the slug. After a move, re-pointing it, or creating a new
  entry, is M6's job. Is anything in M1 hard to change later because of this?
- Device identifiers use `node_key`. Check that the device registry migrates identically. There
  is no explicit device-registry test; entities are tested.
- Is a downgrade path (minor version) worth supporting instead of refusing?

**Tests:** `tests/ha/test_node_key.py` (6). The smoke test exercises a real v1 entry on HA

## 9. App and integration version compatibility

**Files:** `compatibility.py`; `coordinator._update_issues`; translations.

**Rule:**
- Integration N works with app N and N−1.
- A newer app raises "update the integration"; an app more than one minor version behind, or a

**Questions:**

## 10. Container reproducibility and supply chain

**Files:**
- `meshbeacon/Dockerfile` (`ARG SOURCE_DATE_EPOCH` before pip; `rm -f /var/log/apk.log`)
- `.github/workflows/release-dry-run.yaml`
- `tools/verify_image.py`

**Evidence:**
- **Dry run on GitHub's runners:** the pinned HA base, amd64 and arm64 (the latter under QEMU),
  two `--no-cache` builds with `SOURCE_DATE_EPOCH` and `rewrite-timestamp=true`. **Identical
  image manifest digests**, with SPDX SBOM and SLSA provenance attestations, in run 5 on
  `9c4b567`.
- The first runs showed `/var/log/apk.log` as the only differing file. `verify_image` now names
  the differing files.

**Questions:**
- **Same-runner reproducibility only:** both builds run on the same runner, minutes apart.
  Alpine's `apk add --upgrade` resolves *current* package versions, so a rebuild days later will
  differ. Is reproducibility needed across time? If so, pin the apk package versions, or wait
  for a base image that already contains the fixes.
- **Release-time input pinning:** the BuildKit syft scanner image (`docker/buildkit-syft-scanner:stable-1`)
  and QEMU's `tonistiigi/binfmt:latest` are pulled by tag, not digest. Pin them for releases?
- **Base pinning:** the base image is pinned by digest, Python packages by hash, actions by
  SHA. Confirm that the pins are current and correct.
- **Signing (A-3):** the cosign keyless design, and verification against the workflow
  identity, are documented in `docs/releasing.md`. **Not implemented**: that is M2.

- `tests/unit/test_project_identifiers.py`.

**Questions:**
- **Coverage of the guards:** do they catch every way a workflow could publish? Reusable
  workflows, `workflow_call`, composite actions and environment secrets are not checked.

  but it does consume runner time.
- **M2 design:** a protected `release` environment with required reviewers is a repository
  *setting*. A test cannot verify it, so it should go on the release checklist.
