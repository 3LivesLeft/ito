## Found by the new gates in CI

Both of the new gates failed on their first CI run, as intended, and the causes were fixed rather
than the gates relaxed:

| Gate | Finding | Fix |
|---|---|---|
| AppArmor enforcement (M-3) | The narrowed `/run` rules missed s6-linux-init changing the owner and mode of `/run` itself and s6-rc-init's live folder (created with a trailing slash) | Exactly those two rules added; regression paths in `test_apparmor_rules.py` |
| High-with-fix scan (L-4) | GO-2026-5972 in the Go runtime of the base image's `tempio`, which MeshBeacon never uses | `tempio` removed from the image; the build fails if it is still present. (Correction: `THIRD_PARTY_NOTICES` never listed `tempio`. It is documented as an Apache-2.0 base-image component in `docs/research/licensing.md`; the base layer that MeshBeacon redistributes still contains its bytes, hidden by the removal) |

## Residual risks

- **Same-user process separation.** The core and Reticulum still share a Unix user. Isolation of
  the discovery credential rests on the kernel: the core is non-dumpable, so non-root processes
  without `CAP_SYS_PTRACE` (Reticulum among them) cannot read its memory, environment or
  descriptors. Root keeps some `/proc` read access even without that capability (observed in CI's
  test container); root already controls the container. A kernel flaw in those
  checks, or a process gaining `CAP_SYS_PTRACE` inside the container, would defeat it. Separate
  users are a **mandatory, implemented-and-proven gate** before M4 or any community service
  (roadmap IS-1 to IS-4).
- **Legacy HTTP discovery (RR-9a, T73).** The one-time pipe protects the token inside the
  container only. On every released Supervisor the token, the status token and the fingerprint
  still travel in plain HTTP to `http://supervisor`; interception by another app is not
  demonstrated (W3-4, private). No write-capable credential is ever sent this way.
- **Relay restarts.** If the relay restarts, the core's link stays broken until the app restarts;
  the log says so and how to recover. Home Assistant keeps showing the status, because the key only
  changes at an app start (SO-1c).
- **The start step runs as root** for a fraction of a second at each app start (Python, standard
  library only, reading one file or connecting one socket). It is part of the reviewed root surface,
  with the relay.
- **Reproducibility across days** is not expected while the Alpine security layer exists;
  promotion makes it unnecessary for integrity ([releasing](../releasing.md)).
- **Home Assistant test environments** (`requirements-ha-*.txt`) are hash-locked but not audited
  in CI: their versions follow Home Assistant's own pins.
- **Everything platform-level** remains open: see the [VM acceptance tests](../testing/v0.3-vm-acceptance.md).
