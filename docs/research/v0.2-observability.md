Statements are labelled **[Verified]** (by test or by reading the cited source, which is not
reproduced here), **[Assumption]**, **[Recommendation]** or **[Open]**. Upstream revisions:
RNS `1.6.0` (PyPI, unmodified), Supervisor `e610ca8`, Home Assistant Core `dev` at `a779eda`,

## 1. What can be measured reliably

MeshBeacon already runs `RNS.Reticulum` in its own child process (`meshbeacon.node`) and reads
`get_interface_stats()` every 10 s. That method has no leading underscore and is what RNS's own
`rnstatus` uses, but it is **not part of RNS's documented API**, so its keys could change between
RNS versions. **[Recommendation]** Read only an allow-list of keys. Treat a missing key as
"unavailable" (`null`), never as zero. Pin the keys with a contract test against the pinned RNS
version (`tests/integration/test_metrics_rns.py`), so that an RNS upgrade fails loudly rather than
reporting wrong numbers. The figures below were checked on isolated loopback networks (two-node
and three-node).

| Objective | Source | Reliability | Decision |
|---|---|---|---|
| Node status | MeshBeacon's own state machine (`starting`, `running`, `restarting`, `needs_attention`) | **[Verified]** MeshBeacon's own state | Exposed |
| App uptime | Wall-clock time of the core start | **[Verified]** | Exposed as a start timestamp |
| Reticulum uptime | Wall-clock time of the current RNS child start (MeshBeacon's own record) | **[Verified]**. RNS's `transport_uptime` exists only with transport on (`RNS/Reticulum.py` `get_interface_stats`), so MeshBeacon's own record is used in both modes | Exposed as a start timestamp |
| Transport mode status | `RNS.Reticulum.transport_enabled()` (documented API) | **[Verified]** | Exposed, as reported by the *running* RNS, not just as configured |
| Configured peers | Validated settings | **[Verified]** | Count and names only; never host, network name or passphrase |
| Connected peers | Per-interface `status` for `TCPClientInterface` entries | **[Verified]**: false within one status interval after the peer stopped (two-node test) | Exposed per peer |
| Per-peer connection uptime | Not provided by RNS. MeshBeacon records when a peer is first seen up | **[Verified]** to the status interval (10 s); a down-and-up flap shorter than 10 s is not seen | Exposed as "connected since", documented as observed at 10 s resolution |
| Bytes sent and received | Per-interface `rxb`/`txb`; node totals `rxb`/`txb` | **[Verified]**. They reset when RNS restarts, and node totals differ from the sum over interfaces (they are Transport's own counters) | Exposed as totals since the last Reticulum start (HA `total_increasing`, which handles resets) |
| Traffic rates | Computed by MeshBeacon from byte-counter deltas over a 60 s window | **[Verified]** arithmetic; `rxs`/`txs` from RNS are not used (units undocumented) | Exposed in bytes/s; `null` until two samples exist |
| Historical traffic | Home Assistant recorder and long-term statistics | **[Verified]** native HA feature | No MeshBeacon storage at all |
| Known destinations / routing table size | `tpcount` (path table size, `RNS/Transport.py` `path_pool_counts`) | **[Verified]** equals `len(get_path_table())` in test; cheap (no table copy) | Exposed as "known paths". RNS's identity cache (`Identity.known_destinations`) is not exposed through a supported interface, so it is **not** reported |
| Announce activity | Per-interface `arxc`/`atxc` (announces received and sent) | **[Verified]**: matched an announce handler's count exactly | Exposed per peer and in total |
| Forwarded packets | **No public counter.** `rxpkts`/`txpkts` count *all* packets, the node's own included, and cannot be separated | **[Verified]** absent | **Not reported.** Exposing it would mean inventing a metric |
| Forwarding activity (substitute) | `tlinks`/`alinks`: links in Transport's link table, i.e. links relayed **through** this node | **[Verified]**: in a three-node test (A ↔ MeshBeacon ↔ B, transport on), a link from B to A showed `tlinks = 1`; 0 with transport off. Entries remain until RNS expires them, so this lags a peer going away | Exposed as "relayed links" with that caveat. It shows that forwarding is happening, not how much |
| Total packets | `rxpkts`/`txpkts` | **[Verified]** | Exposed, labelled "including the node's own" |
| CPU and memory | `/proc/<pid>/stat`, `/proc/<pid>/status` (RSS + swap) for the core and RNS, as v0.1's guards already do | **[Verified]** | Exposed: memory per process and in total; CPU as a 60 s average, % of one core |
| Reconnection counts | MeshBeacon counts down→up transitions per peer | **[Verified]**; same 10 s resolution caveat | Exposed since the app started |
| Reticulum service restarts | MeshBeacon's restart policy (crash, stall, memory guard) | **[Verified]** | Exposed since the app started; memory-guard restarts also counted separately |
| Diagnostic states | A stable `problem` code with the existing plain-language message | **[Verified]** | Exposed; drives HA repair issues |

**Not used, on purpose:** identity and destination hashes, `transport_id`, `network_id`, interface
`hash`, IFAC fields, `probe_responder`, the path table's entries, the rate table, blackhole lists
and discovery data. They identify the node or others, and monitoring does not need them.

## 2. Options considered for Home Assistant

| Option | Privileges | Problems | Verdict |
|---|---|---|---|
| **A. Custom integration polling a token-authenticated local API, token delivered by Supervisor discovery** | None new. `discovery: [meshbeacon]` in `config.yaml`; posting a discovery message needs no `hassio_api` (`/discovery.*` is in the Supervisor's app API bypass, `api/middleware/security.py`, `e610ca8`) | One new authenticated internal listener while the option is on | **Chosen** |
| B. App writes entities through the HA Core API (`homeassistant_api: true`) | The app gains write access to all of HA | No device registry, no statistics metadata, and it breaks the "app cannot touch HA" principle | Rejected |
| C. MQTT discovery | Needs an MQTT broker and credentials; the app talks to a third service | Any MQTT client with broker access can read the topics; adds a dependency | Rejected |
| D. Unauthenticated read-only API on the internal network | None | Every other app on the `hassio` network could read peer names and traffic | Rejected |
| E. Ingress web UI as the overview | `ingress: true` (rating unchanged at 8) | A second monitoring implementation, with its own history and charts | Rejected for v0.2; a dashboard of native cards is supplied instead (§4) |

**[Verified]** Discovery does not change the security rating: `rating_security`
(`supervisor/apps/utils.py`, `e610ca8`) has no term for discovery, so the rating stays at 8
(5, +1 AppArmor profile, +2 for no host network and no ports).

**[Verified]** Supervisor discovery messages can be read only by Home Assistant Core: `GET
/discovery` and `GET /discovery/{uuid}` are `@require_home_assistant` (`api/discovery.py`). An app
can post only services listed in its own `config.yaml`. A changed `config` for the same service
updates the existing message and pushes it to Core again (`discovery/__init__.py` `send`). Core
starts the integration's `hassio` config flow with that config (`components/hassio/discovery.py`,
Core `a779eda`).

## 3. Architecture

```text
 HA Core ── custom_components/meshbeacon ── HTTPS GET /api/v1/status, every 60 s ───────────┐
   │  (bearer token; certificate pinned by fingerprint)                                     │
   │  entities, repair issues, diagnostics; history and statistics in HA's recorder         ▼
   │                               ┌─ MeshBeacon app container (bridged hassio network) ───────────┐
   │   discovery: host, port,      │ meshbeacon.supervisor (user meshbeacon)                       │
   └── token, cert fingerprint ◄───┤   metrics.Collector ← status JSON from meshbeacon.node (10 s) │
       (via the Supervisor; only   │   :8099 /health (open, bounded)                               │
        HA Core can read it)       │   :8100 /api/v1/status (TLS 1.3 + token, opt-in, bounded)     │
                                   │   meshbeacon.node → RNS (unmodified)                          │
                                   └───────────────────────────────────────────────────────────────┘
```

- **One monitoring implementation.** The core's `metrics.Collector` is the only place where
  metrics are computed. The API serves a snapshot it has already built. The integration only maps
  fields to entities, and the dashboard only arranges native cards. History lives in HA's recorder.
  MeshBeacon stores no metrics on disk.
- **Isolated from Reticulum.** Every metrics call, every snapshot rebuild and the discovery thread
  are wrapped. A failure in monitoring is logged at most hourly and never reaches the loop that
  supervises Reticulum (tested by breaking every collector method).
- **Separate, bounded listeners.**

  | Listener | Port | Concurrent connections | Inactivity timeout | Absolute deadline |
  |---|---|---|---|---|
  | Status API (only while the option is on) | 8100 | 4 | 5 s | 10 s |
  | Watchdog `/health` (its own server) | 8099 | 16 | 5 s | 5 s |

  Connections over the limit are closed at once. Client-caused errors are counted, never printed.
- **Encrypted and pinned.** Each start makes a throwaway P-256 certificate in a short-lived process
  (`meshbeacon.tlscert`), which keeps the 13 MB `cryptography` import out of the core. The key is on
  disk, 0600 in a private temporary directory, only while it is loaded. TLS 1.3 only. The handshake
  runs in the connection's own thread under its deadline. The SHA-256 fingerprint travels in the
  discovery message, and the integration pins it with `aiohttp.Fingerprint`, which checks it before
  the key is sent. There is no plain-HTTP fallback in either direction.
- **Token.** 256 random bits, generated **in memory at every core start**, compared with
  `hmac.compare_digest`. It is never written to `/data` and never logged. It reaches Home Assistant
  only through discovery.
- **Discovery.**
  - It retries with back-off from 30 s to 15 min until the Supervisor answers.
  - It then re-sends the unchanged message every 6 h; the Supervisor drops exact duplicates without
    disturbing HA.
  - Switching the option off withdraws the message, using its recorded UUID, which is not secret.
- **Self-healing.** If Home Assistant missed the push after a key rotation, the integration reads
  its own app's message from the Supervisor (`hassio.get_supervisor_client`, matched by slug, at
  most every 5 minutes). HA also replays every stored discovery message at its own start, so start-up
  order does not matter.
- **Supervisor token.** The run script passes `SUPERVISOR_TOKEN` to the core only when it exists.
  The core removes it from its environment, so neither `prepare`, `tlscert` nor RNS ever receives it.
- **Opt-in, permanently.** `home_assistant_integration` defaults to **off**. When it is off there is
  no listener on 8100 and no discovery: exactly v0.1's behaviour.
- **Layering kept.** The integration never imports `RNS` or the core. It validates schema 1 itself,
  and a contract test feeds the core's real output through the integration's parser.

## 4. Entities, names and dashboard

One device, **MeshBeacon**. Peer entities belong to it and are named after the peer, for example
"Emerald connected". Peers are not devices, and HA 2026.10 deprecates `via_device` links. Names are
plain UK English, with a unit or qualifier wherever a bare word could mislead.

| Entity (default name) | Class and state class | Category | Enabled by default |
|---|---|---|---|
| Status | enum | — | Yes |
| Connectivity | enum | — | Yes |
| Problem (binary, `problem`) | — | — | Yes |
| Problem details | enum | diagnostic | Yes |
| Reticulum running; Transport mode (binary) | `running`; — | diagnostic | Yes |
| App started; Reticulum started | `timestamp` | diagnostic | Yes |
| Peers connected | measurement | — | Yes |
| Peers configured | measurement | diagnostic | Yes |
| Data received; Data sent | `data_size`, `total_increasing` | — | Yes |
| Receive rate; Send rate (whole B/s) | `data_rate`, measurement | — | Yes |
| Known paths | measurement | — | Yes |
| **Links relayed for others** | measurement | — | Yes |
| Memory use (whole MiB) | `data_size`, measurement | diagnostic | Yes |
| Processor use (0.1 %) | %, measurement | diagnostic | Yes |
| Reticulum restarts; Memory-limit restarts | `total_increasing` | diagnostic | Yes |
| Packets received/sent (all traffic) | `total_increasing` | diagnostic | No |
| Announces received/sent | `total_increasing` | diagnostic | No |
| Memory use (MeshBeacon core / Reticulum) | `data_size` | diagnostic | No |
| *Peer* connected (binary, `connectivity`) | — | — | Yes |
| *Peer* connected since | `timestamp` | — | Yes |
| *Peer* reconnections | `total_increasing` | diagnostic | Yes |
| *Peer* data received/sent, receive/send rate, announces | as above | mixed | No |

**Relayed links versus forwarded packets.** "Links relayed for others" counts Reticulum links
carried *through* this node in transport mode. It shows that the node helps other people, but not
how much traffic it moves for them. Reticulum reports no forwarded-packet count, and MeshBeacon
does not estimate one. The entity name, the dashboard note, the app documentation and the
integration guide all say so. "Packets … (all traffic)" includes the node's own packets.

**Repair issues:**
- `isolated`.
- `peers_unreachable`, after 10 minutes, so short outages do not nag.
- `needs_attention`, with the app's message.

**Diagnostics** contain the last snapshot and the entry data. The token and host are removed, and
peer names are replaced.

**Dashboard.** [`dashboard.yaml`](../home-assistant/dashboard.yaml) uses only native cards and only
entities enabled by default; a test checks every entity it names.

## 5. Security review (revised after independent review)

### 5.1 Trust boundaries

| Party | Trusted for | Notes |
|---|---|---|
| Supervisor | Everything (it controls all containers) | Delivers discovery; sets the sending app's slug from its own credentials |
| HA Core | Reading discovery messages; storing the integration's entry | Only HA Core may `GET /discovery` (verified) |
| Other apps on the `hassio` network | **Nothing** | Can reach port 8100. By default they hold `NET_RAW`, so they can ARP-spoof (verified, Supervisor `e610ca8`) |
| Apps or users with access to HA's `/config` (file editors, Samba, admins) | Already trusted with every HA secret | Can read the integration's entry (token and fingerprint) |
| Full-access or privileged apps | Can do anything on the host | Out of scope ([threat model T26](../security/threat-model.md)) |

### 5.2 Findings and controls

| Threat | Control | Evidence |
|---|---|---|
| Another app reads metrics directly | Bearer token; no listener while the option is off | `test_api.py`, integration tests |
| Another app intercepts or alters HA ↔ MeshBeacon traffic (ARP spoofing with `NET_RAW`) | TLS 1.3 with a per-start certificate pinned by the fingerprint from discovery; the key is sent only after the pin matches | `test_status_api_is_https_only_with_a_fresh_pinned_certificate`; the real-HA smoke test uses aiohttp's pinning |
| Another app posts a `meshbeacon` discovery message to redirect the integration or capture credentials | Accepted only from a MeshBeacon slug, with the host equal to that app's own hostname and a fingerprint present. It cannot update another app's entry, because entries are keyed by slug and the Supervisor sets the slug. A look-alike from another repository gets its own confirmation dialog naming the app and slug. The integration sends each app only the token that app gave it, so nothing can be captured | `tests/ha/test_security.py` |
| Token leaks through logs, exceptions, flow listings or diagnostics | Never logged by the app or the integration. Errors carry only the exception class and host. Diagnostics redact token and host. Flow listings carry no data | Tests with debug logging under 401, 500, connection errors, timeouts, bad JSON and schema mismatch |
| Slow clients and floods | Concurrency caps, inactivity timeout and absolute deadline on both servers | 30 s flood test; trickling-client and stalled-handshake unit tests |
| Supervisor token reaches RNS | Removed from all child environments | `/proc/<pid>/environ` checks |
| Timing attack on the token | `hmac.compare_digest`; refusals summarised at most hourly | `test_api.py` |

### 5.3 Where the token and certificate are stored

| Location | Contents | Readable by | Lifetime |
|---|---|---|---|
| MeshBeacon process memory | Token, TLS key | Nobody else | Until the core stops |
| MeshBeacon `/data` (and so MeshBeacon's backups) | Only the discovery message's UUID (`discovery.json`) | — | Until withdrawn |
| Temporary key file | TLS private key, 0600 in a private directory | Service user | Milliseconds; deleted after loading (tested) |
| Supervisor's own data | The discovery message (token, fingerprint) | Supervisor, and HA Core through the API | Until replaced, withdrawn or the app is removed |
| HA config entry (`/config/.storage/core.config_entries`, plain JSON) | Token, fingerprint, host, port | HA admins, apps that map `/config`, anyone holding an HA backup | Until the next MeshBeacon start |
| HA backups | Same, as part of `/config` | Anyone who can open the backup (encrypted by default for HA's automatic backups) | The token is **useless after the next MeshBeacon start** |

## 6. Update frequency and recorder storage

| | Before the review | Now |
|---|---|---|
| Integration polling | 30 s | **60 s**, matching the core's 60 s rate window; the watchdog acts on 120 s |
| Core status from RNS | 10 s | 10 s |
| Entities enabled by default (1 peer) | 33 | **23**; each extra peer adds 3 that rarely change |
| Recorder rows per poll, worst case (every value changing) | ~15 | **~6** |
| Recorder growth, worst case | ~8.3 MB/day with 1 peer, ~35 MB/day with 10 | **~1.9 MB/day**, almost independent of the number of peers |
| Over HA's default 10-day history | ~83 MB (1 peer) | **~19 MB** |

Measured with the HA test harness and a file-backed SQLite recorder: 120 polls with every value
changing, at about 190–216 bytes per state row including indexes. In normal use most values stay
the same from poll to poll, so the real load is lower.

Long-term statistics are HA's own hourly aggregates for the measurement and total sensors, and add
little. Users who enable the detailed entities accept more rows. Recorder `exclude` can remove any
entity.

## 8. Residual risks

| ID | Risk | Likelihood / impact | Why accepted, and possible mitigation |
|---|---|---|---|
| RR-1 | Anyone who can read HA's `/config` or an HA backup holds the current token and can read the metrics until MeshBeacon restarts | Low / low (read-only, non-identifying) | They already hold every HA secret. *Possible later:* rotate the token while running (for example daily) |
| RR-2 | A malicious app floods port 8099 above 16 concurrent connections for long enough that two watchdog checks in a row fail. The Supervisor restarts the app, and after five such restarts start-history safe mode stops Reticulum | Low / medium (denial of service) | Needs a hostile app that can also exhaust the host in other ways. The bound keeps the core alive (a 30 s flood test passed). The watchdog is off by default |
| RR-3 | The user confirms a look-alike app's discovery (another repository's `*_meshbeacon`) and sees false metrics | Low / low | The dialog names the app and slug, and it cannot affect the real entry |
| RR-4 | Pinning relies on HA Core and the Supervisor keeping discovery confidential | Low | Both are already fully trusted |
| RR-5 | Option switched off after `discovery.json` was lost: a stale message stays at the Supervisor | Low / none | Its token and certificate die with the next start; HA ignores messages from stopped apps |
| RR-6 | Metric limits: 10 s resolution for connection changes; relayed links lag RNS's link expiry; counters reset when Reticulum restarts (HA's `total_increasing` handles it) | — | Documented |
| RR-7 | The pytest harness lags Home Assistant (2026.10.4 only), so 2026.11.2 is covered by strict typing and a real-HA smoke test, not by the full suite | — | CI job `home-assistant-release`; rerun the harness when one for 2026.11 is published |
| RR-8 | HTTPS adds a handshake per poll and about 3 MB for Python's `ssl` module in the core | — / low | Measured; within budget |

## 9. Onboarding

| Step | Who | Manual? |
|---|---|---|
| Install the integration (copy `custom_components/meshbeacon` to `/config/custom_components/`, restart HA) | User | Yes, once. A HACS custom-repository install would make this one step, but needs a maintainer decision because the repository would then be an install source |
| Switch on **Show MeshBeacon's status in Home Assistant**, restart the app | User | Yes, once |
| Discovery, key exchange, certificate pinning | Automatic | No |
| **Add** on "MeshBeacon discovered" | User | One click |
| Key rotation, Supervisor or HA restarts, start-up order | Automatic | No |

Order does not matter: HA replays stored discovery messages at start-up (verified, Core
`components/hassio/discovery.py`), so installing the integration after enabling the option works
after HA's restart. Once discovery succeeds, the app log tells the user where to click and what to do
if nothing appears.

## 10. Out of scope (unchanged)

LXMF, LoRa/RNode, I2P, any remote control or write endpoint, identity import, an Ingress UI,
telemetry, and publishing images or releases.
