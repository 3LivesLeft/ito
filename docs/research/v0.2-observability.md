`192db5f` (the reviewed head of PR #2). Decision record: [ADR 0006](../adr/0006-local-metrics-api.md).
Acceptance criteria: [roadmap §v0.2.0](../roadmap.md#v020-acceptance-criteria).

Statements are labelled **[Verified]** (by test or by reading the cited source, which is not
reproduced here), **[Assumption]**, **[Recommendation]** or **[Open]**. Upstream revisions:
RNS `1.6.0` (PyPI, unmodified), Supervisor `e610ca8`, Home Assistant Core `dev` at `a779eda`,

## 1. What can be measured reliably

MeshBeacon already runs `RNS.Reticulum` in its own child process (`meshbeacon.node`) and reads
`get_interface_stats()` every 10 s. That method has no leading underscore and is what RNS's own
`rnstatus` uses, but it is **not part of RNS's documented API**, so its keys could change between
RNS versions. **[Recommendation]** Read only an allow-list of keys. Treat a missing key as
"unavailable" (`null`), never as zero. Pin the keys with a contract test against the pinned RNS
version (`tests/integration/test_metrics_rns.py`), so that an RNS upgrade fails loudly rather than
reporting wrong numbers. The figures below were checked on isolated loopback networks (two-node
and three-node).

| Objective | Source | Reliability | Decision |
|---|---|---|---|
| Node status | MeshBeacon's own state machine (`starting`, `running`, `restarting`, `needs_attention`) | **[Verified]** MeshBeacon's own state | Exposed |
| App uptime | Wall-clock time of the core start | **[Verified]** | Exposed as a start timestamp |
| Reticulum uptime | Wall-clock time of the current RNS child start (MeshBeacon's own record) | **[Verified]**. RNS's `transport_uptime` exists only with transport on (`RNS/Reticulum.py` `get_interface_stats`), so MeshBeacon's own record is used in both modes | Exposed as a start timestamp |
| Transport mode status | `RNS.Reticulum.transport_enabled()` (documented API) | **[Verified]** | Exposed, as reported by the *running* RNS, not just as configured |
| Configured peers | Validated settings | **[Verified]** | Count and names only; never host, network name or passphrase |
| Connected peers | Per-interface `status` for `TCPClientInterface` entries | **[Verified]**: false within one status interval after the peer stopped (two-node test) | Exposed per peer |
| Per-peer connection uptime | Not provided by RNS. MeshBeacon records when a peer is first seen up | **[Verified]** to the status interval (10 s); a down-and-up flap shorter than 10 s is not seen | Exposed as "connected since", documented as observed at 10 s resolution |
| Bytes sent and received | Per-interface `rxb`/`txb`; node totals `rxb`/`txb` | **[Verified]**. They reset when RNS restarts, and node totals differ from the sum over interfaces (they are Transport's own counters) | Exposed as totals since the last Reticulum start (HA `total_increasing`, which handles resets) |
| Traffic rates | Computed by MeshBeacon from byte-counter deltas over a 60 s window | **[Verified]** arithmetic; `rxs`/`txs` from RNS are not used (units undocumented) | Exposed in bytes/s; `null` until two samples exist |
| Historical traffic | Home Assistant recorder and long-term statistics | **[Verified]** native HA feature | No MeshBeacon storage at all |
| Known destinations / routing table size | `tpcount` (path table size, `RNS/Transport.py` `path_pool_counts`) | **[Verified]** equals `len(get_path_table())` in test; cheap (no table copy) | Exposed as "known paths". RNS's identity cache (`Identity.known_destinations`) is not exposed through a supported interface, so it is **not** reported |
| Announce activity | Per-interface `arxc`/`atxc` (announces received and sent) | **[Verified]**: matched an announce handler's count exactly | Exposed per peer and in total |
| Forwarded packets | **No public counter.** `rxpkts`/`txpkts` count *all* packets, the node's own included, and cannot be separated | **[Verified]** absent | **Not reported.** Exposing it would mean inventing a metric |
| Forwarding activity (substitute) | `tlinks`/`alinks`: links in Transport's link table, i.e. links relayed **through** this node | **[Verified]**: in a three-node test (A ↔ MeshBeacon ↔ B, transport on), a link from B to A showed `tlinks = 1`; 0 with transport off. Entries remain until RNS expires them, so this lags a peer going away | Exposed as "relayed links" with that caveat. It shows that forwarding is happening, not how much |
| Total packets | `rxpkts`/`txpkts` | **[Verified]** | Exposed, labelled "including the node's own" |
| CPU and memory | `/proc/<pid>/stat`, `/proc/<pid>/status` (RSS + swap) for the core and RNS, as v0.1's guards already do | **[Verified]** | Exposed: memory per process and in total; CPU as a 60 s average, % of one core |
| Reconnection counts | MeshBeacon counts down→up transitions per peer | **[Verified]**; same 10 s resolution caveat | Exposed since the app started |
| Reticulum service restarts | MeshBeacon's restart policy (crash, stall, memory guard) | **[Verified]** | Exposed since the app started; memory-guard restarts also counted separately |
| Diagnostic states | A stable `problem` code with the existing plain-language message | **[Verified]** | Exposed; drives HA repair issues |

**Not used, on purpose:** identity and destination hashes, `transport_id`, `network_id`, interface
`hash`, IFAC fields, `probe_responder`, the path table's entries, the rate table, blackhole lists
and discovery data. They identify the node or others, and monitoring does not need them.

## 2. Options considered for Home Assistant

| Option | Privileges | Problems | Verdict |
|---|---|---|---|
| **A. Custom integration polling a token-authenticated local API, token delivered by Supervisor discovery** | None new. `discovery: [meshbeacon]` in `config.yaml`; posting a discovery message needs no `hassio_api` (`/discovery.*` is in the Supervisor's app API bypass, `api/middleware/security.py`, `e610ca8`) | One new authenticated internal listener while the option is on | **Chosen** |
| B. App writes entities through the HA Core API (`homeassistant_api: true`) | The app gains write access to all of HA | No device registry, no statistics metadata, and it breaks the "app cannot touch HA" principle | Rejected |
| C. MQTT discovery | Needs an MQTT broker and credentials; the app talks to a third service | Any MQTT client with broker access can read the topics; adds a dependency | Rejected |
| D. Unauthenticated read-only API on the internal network | None | Every other app on the `hassio` network could read peer names and traffic | Rejected |
| E. Ingress web UI as the overview | `ingress: true` (rating unchanged at 8) | A second monitoring implementation, with its own history and charts | Rejected for v0.2; a dashboard of native cards is supplied instead (§4) |

**[Verified]** Discovery does not change the security rating: `rating_security`
(`supervisor/apps/utils.py`, `e610ca8`) has no term for discovery, so the rating stays at 8
(5, +1 AppArmor profile, +2 for no host network and no ports).

**[Verified]** Supervisor discovery messages can be read only by Home Assistant Core: `GET
/discovery` and `GET /discovery/{uuid}` are `@require_home_assistant` (`api/discovery.py`). An app
can post only services listed in its own `config.yaml`. A changed `config` for the same service
updates the existing message and pushes it to Core again (`discovery/__init__.py` `send`). Core
starts the integration's `hassio` config flow with that config (`components/hassio/discovery.py`,
Core `a779eda`).

## 3. Architecture

```text
 HA Core ── custom_components/meshbeacon ── GET /api/v1/status (Bearer token, every 30 s) ──┐
   │  entities, repair issues, diagnostics; history and statistics in HA's recorder         │
   │                                                                                        ▼
   │                               ┌─ MeshBeacon app container (bridged hassio network) ───────────┐
   │   discovery (token, host,     │ meshbeacon.supervisor (user meshbeacon)                       │
   └── port) via Supervisor ◄──────┤   metrics.Collector ← status JSON from meshbeacon.node (10 s) │
                                   │   :8099 /health (open)   :8100 /api/v1/status (token, opt-in) │
                                   │   meshbeacon.node → RNS (unmodified)                          │
                                   └───────────────────────────────────────────────────────────────┘
```

- **One monitoring implementation.** The core's `metrics.Collector` is the only place where
  metrics are computed. The API serves a snapshot it has already built, so a request costs one
  JSON serialisation. The integration only maps fields to entities, and the dashboard only arranges
  native cards. History lives in HA's recorder. MeshBeacon stores no metrics on disk.
- **Separate listener.** The API has its own port (8100) and server, started only when the option is
  on, so a flood of API requests can never starve the watchdog's `/health` (port 8099).
- **Bounded.** The node writes one status line per 10 s. At most 10 peers are allowed, so a line
  stays well under the 8 kB line limit. Rate windows hold at most 7 samples per counter. The HTTP
  server serves at most 4 requests at a time (others are closed at once), with a 5 s socket
  timeout, request lines and headers capped by the standard library, GET only and no bodies.
  The integration polls every 30 s, fixed.
- **Token.** 256 random bits, generated **in memory at every core start**, compared with
  `hmac.compare_digest`. It is never written to `/data`, so it is not in MeshBeacon's backups, and
  it is never logged. It reaches Home Assistant only through discovery. Every app restart rotates
  it; the integration's discovery step updates its stored token and reloads.
- **Supervisor token.** The run script passes `SUPERVISOR_TOKEN` to the core only when it exists.
  The core removes it from its environment after reading it, so neither `prepare` nor RNS ever
  receives it. It is used only for `POST http://supervisor/discovery`, with three attempts and a
  10 s timeout each. A failure is logged in plain language and is never fatal.
- **Opt-in.** A new option, `home_assistant_integration` (default **off** until ADR 0006 is
  approved). When it is off, `/api/v1/status` answers 404 and no discovery is sent. That matches
  v0.1 behaviour exactly.
- **Layering kept.** The integration never imports `RNS` or the core. It validates the versioned
  JSON schema (`schema: 1`) itself, and a contract test feeds the core's real output through the
  integration's parser.

## 4. Entities and dashboard

One device, "MeshBeacon". Peer entities belong to it and are named after the peer (for example
"Emerald connected"). Peers are not devices, and HA 2026.10 deprecates `via_device` links.

| Entity | Platform | Class and state class | Category |
|---|---|---|---|
| Status (`running`, `starting`, `restarting`, `needs_attention`) | sensor (enum) | — | — |
| Connectivity (`isolated`, `offline`, `partial`, `online`, `unknown`) | sensor (enum) | — | — |
| Diagnosis (problem code) | sensor (enum) | — | diagnostic |
| Problem | binary sensor (`problem`) | — | — |
| Transport mode | binary sensor | — | diagnostic |
| Reticulum running | binary sensor (`running`) | — | diagnostic |
| App started, Reticulum started | sensor | `timestamp` | diagnostic |
| Peers connected, peers configured | sensor | measurement | — / diagnostic |
| Received, sent | sensor | `data_size`, B, `total_increasing` | — |
| Receive rate, send rate | sensor | `data_rate`, B/s, measurement | — |
| Packets received and sent (including own) | sensor | `total_increasing` | diagnostic |
| Known paths | sensor | measurement | — |
| Relayed links | sensor | measurement | — |
| Announces received, sent | sensor | `total_increasing` | diagnostic |
| Memory (total; core; Reticulum) | sensor | `data_size`, measurement | diagnostic |
| CPU | sensor | %, measurement | diagnostic |
| Reticulum restarts, memory-guard restarts | sensor | `total_increasing` | diagnostic |
| Per peer: connected | binary sensor (`connectivity`) | — | — |
| Per peer: connected since | sensor | `timestamp` | — |
| Per peer: received, sent, rates, announces, reconnections | sensor | as above | rates and announces diagnostic |

Repair issues: `isolated`, `peers_unreachable` (after 10 minutes, so short outages do not nag) and
`needs_attention` (with the app's message). Diagnostics download: the coordinator's last snapshot
and the entry data, with the token and host redacted and peer names replaced. An example dashboard
of native cards (`docs/home-assistant/dashboard.yaml`) gives the simple overview with history graphs and
statistics graphs. It is a view of the same entities, not a second implementation.

## 5. Security review of the new interface

Updates to the [threat model](../security/threat-model.md) (T11, T28–T33):

| Threat | Control |
|---|---|
| Another app on the `hassio` network reads metrics | Bearer token; 404 when the integration option is off; nothing on a published port |
| Token theft from backups or logs | Not on disk in the app; never logged; rotated each start. HA stores it in its config entry, which HA's own backups protect |
| Resource exhaustion through the API | ≤ 4 concurrent requests, 5 s timeout, GET only, no bodies, cached snapshot. `/health` is exempt from the request limit, so the watchdog is never starved |
| Identity or peer-credential disclosure | Allow-listed fields; no hashes, hosts, network names or passphrases; a test asserts that the serialised snapshot contains none of them |
| Supervisor token leaks to RNS | Read once by the core, removed from the environment; children receive an environment without it (tested) |
| Timing attack on the token | `hmac.compare_digest`; failed attempts counted and summarised in the log at most hourly, never echoed |

**[Open]** HTTP on the internal Docker bridge is unencrypted, like every app-to-Core link on
HA OS. An attacker who can sniff that bridge already controls the host.

## 6. Resource budget

| Item | Budget | Measured |
|---|---|---|
| Idle memory, whole app, integration option on | ≤ 128 MB (RSS + swap, all processes) | 71.3 MiB (69.2 MiB with it off), amd64 container on the stand-in base: [phase 2 results](../testing/phase2-results.md) |
| Added CPU of collection | < 0.1 % of one core averaged | One JSON parse per 10 s plus `/proc` reads |
| Disk | 0 bytes of metric storage in the app | — |
| HA side | One HTTP request per 30 s; about 30 entities plus 10 per peer, all at fixed intervals | — |

## 7. Out of scope (unchanged)

LXMF, LoRa/RNode, I2P, any remote control or write endpoint, identity import, an Ingress UI,
telemetry, and publishing images or releases.
