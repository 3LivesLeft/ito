# v0.3.0 Messaging: feasibility review and proposed architecture

**Status: research and architecture only.** Nothing here is implemented. **v0.3.0 must not be
implemented until this document, ADRs 0008–0012 and the threat-model additions have been
independently reviewed and approved by the maintainer.**

- **Branch:** `research/v0.3.0-messaging`, based on the v0.2 work (`claude/bold-tesla-dhu5zo`, on
  top of draft PR #3).
- **Date:** 18 November 2026.
- **Priorities, in order of tie-break:** privacy, reliability, simplicity, resource efficiency.
- **Labels:** **[Verified]** (checked against source or a primary document, with the version cited),
  **[Assumption]** (believed true but not checked), **[Recommendation]**, **[Open]**.
- **Source reading follows the project rules.** Behaviour of `lxmf` 1.3.1 and `rns` 1.6.1 from PyPI
  was read to verify it, and is described here, not reproduced (CLAUDE.md rules 1 and 11). File
  names are given so a reviewer can check.

## 1. Summary

| Question | Answer |
|---|---|
| Is native LXMF with **unmodified upstream libraries** feasible? | **Yes.** `LXMF.LXMRouter` and `LXMF.LXMessage` provide sending, receiving, delivery proofs, propagation-node use and hosting, stamps (proof of work), tickets, ratchets and storage limits through public methods. No monkeypatching or private attributes are needed (§3) |
| Interoperable with **Sideband** and **Ratspeak**? | **Likely, with conditions.** Both currently state RNS 1.6.0 and LXMF 1.3.0 (§4). LXMF is the shared wire format, so interoperability means the same LXMF version family plus compatible stamp costs. It must be proven with a test matrix before release (MS-14) |
| Sending and receiving through **Home Assistant**? | **Yes, but it adds MeshBeacon's first write path** (HA → app). That is a security change, which needs ADR 0010 and a separately scoped key (§6) |
| **Notifications, actions and automation events**? | Yes: a `notify` entity per contact, an `event` entity for received messages and delivery status, a `meshbeacon.send_message` action that returns the message ID, and a blueprint for actionable mobile notifications. **Message content is not recorded by default** (§6.3) |
| **Persistent queues and delivery receipts**? | LXMF's outbound queue is **memory-only** **[Verified]**. MeshBeacon needs a small, bounded SQLite queue that survives restarts, plus a mapping of LXMF states to receipts (§5) |
| **Offline delivery**? | Three cases (§5.3): recipient offline (propagation node), MeshBeacon offline (fetch from the propagation node), Home Assistant offline (inbound held in the app until acknowledged) |
| **Optional propagation node**? | Feasible through `enable_propagation()`. **[Recommendation]** off by default, static peers only, disk quota, and delivered *after* the core messaging (phase 3b, ADR 0012) |
| **Resource use** on a Raspberry Pi? | Memory of a second RNS client process and the CPU cost of stamp generation are the unknowns. Budgets and measurements are in §8, and they are release gates |
| Can v0.3.0 stay **simple**? | Yes, if it is **text-only**, has **one household messaging identity**, has **contacts-only inbound by default**, and has **no attachments, groups, telemetry or commands** (§2) |

**Pin finding.** `lxmf` **1.3.1** (newest on PyPI) requires `rns>=1.6.1` **[Verified]**
(package metadata). MeshBeacon pins `rns==1.6.0`. v0.3 needs both bumped together, through the
project's RNS-pin process: the full isolated-network suite plus the known-paths canary test.

## 2. Scope of v0.3.0 (proposed)

| In | Out (later, separate ADRs) |
|---|---|
| Text messages (title optional), UTF-8, ≤ 8 KiB content | Attachments, images, audio, voice (LXST), telemetry, location |
| One messaging identity for the household (ADR 0009) | Several identities, per-user identities |
| Contacts: an allow-list of LXMF addresses with local names | Address-book sync, contact discovery from announces |
| Direct and opportunistic delivery; propagated delivery through one chosen node | Automatic node selection from announces |
| Inbound from contacts only, by default; an optional "from anyone, with stamps" mode | Public inbox, groups, channels (RRC) |
| HA: notify entities, an event entity, a send action with a response, receipts | **Commands from messages (v0.6)**, any HA control from LXMF |
| Optional propagation node (phase 3b) | Public propagation node with auto-peering on by default |

Anything not listed as in is out.

## 3. LXMF capabilities (verified, `lxmf` 1.3.1)

| Capability | Public API (file) | Notes |
|---|---|---|
| Router with on-disk state | `LXMRouter(identity, storagepath, …)` (`LXMRouter.py`) | Options include `autopeer`, `propagation_limit` (KB, default 256), `delivery_limit` (KB, default 1000), `enforce_ratchets`, `enforce_stamps`, `static_peers`, `max_peers`, `from_static_only`, propagation and peering costs |
| Receive | `register_delivery_identity(identity, display_name, stamp_cost)`, `register_delivery_callback(fn)` | The delivery destination enables **ratchets** automatically (forward secrecy); `enforce_ratchets` refuses senders without them |
| Send | `LXMessage(destination, source, content, title, fields, desired_method)`, `router.handle_outbound(msg)` | Methods `OPPORTUNISTIC`, `DIRECT`, `PROPAGATED` (and `PAPER`) |
| Receipts | `msg.register_delivery_callback`, `register_failed_callback`; `msg.state` | States: `OUTBOUND`, `SENDING`, `SENT`, `DELIVERED`, `REJECTED`, `CANCELLED`, `FAILED` |
| What "delivered" means | `LXMessage.py` | **[Verified]** `DELIVERED` is set by a delivery proof from the recipient (direct or opportunistic). For propagated messages the state becomes `SENT` once the **propagation node** accepts the message. That is *not* proof that the recipient has it |
| Retries | `LXMRouter.MAX_DELIVERY_ATTEMPTS = 5`, `DELIVERY_RETRY_WAIT = 10` s | After the attempts the message `FAILED`. **[Verified]** there is no automatic fall-back to propagation in 1.3.1, so MeshBeacon must resubmit as `PROPAGATED` |
| Outbound queue persistence | `router.pending_outbound` (a list in memory) | **[Verified]** not saved at exit, unlike transient IDs, tickets and stamp costs, which are. MeshBeacon keeps its own queue (ADR 0011) |
| Inbound de-duplication | locally delivered transient IDs (saved) | Duplicates are suppressed across restarts by LXMF itself |
| Signature check | `msg.signature_validated`, `msg.unverified_reason` (`SOURCE_UNKNOWN`, `SIGNATURE_INVALID`) | A message from a sender whose identity is not yet known cannot be verified |
| Spam controls | `set_inbound_stamp_cost`, `enforce_stamps()`, tickets (`generate_ticket`, `FIELD_TICKET`), `ignore_destination` | Stamps are proof of work: costly to send, cheap to check. Tickets let chosen contacts skip the stamp |
| Storage limits | `set_message_storage_limit()`, `set_information_storage_limit()`; `MESSAGE_EXPIRY` = 30 days | The propagation store is bounded and expires |
| Propagation node | `enable_propagation()`, `set_authentication()`, `allow()`, `static_peers`, `from_static_only`, `max_peers`; the `lxmd` utility | Peering and sync costs are configurable; nodes check propagation stamps |
| Fetch from a node | `set_outbound_propagation_node()`, `request_messages_from_propagation_node(identity)` | Used for "MeshBeacon was offline" |
| What a node can see | `LXMessage.py`, propagated packing | **[Verified]** a propagated message is the destination hash in clear, followed by data encrypted to the destination. The sender, title, content and fields are inside the encryption. The node learns the **recipient hash, size and timing** |
| Encryption labels | `ENCRYPTION_DESCRIPTION_EC` (Curve25519), `…_AES` (AES-256) | End-to-end between LXMF identities; RNS provides the primitives (no project cryptography, rule 2) |

## 4. Interoperability: Sideband and Ratspeak

| Client | Current release (source) | Stack | Notes |
|---|---|---|---|
| **Sideband** | 2.3.0 (release notes, [newreleases.io](https://newreleases.io/project/github/markqvist/Sideband/release/2.3.0)) | RNS 1.6.0, LXMF 1.3.0, LXST 0.6.0 | Generates **destination stamps** at first start after upgrading; supports RNS network stamps. CC BY-NC-SA: we may *run* it for testing, never reuse its code ([licensing](licensing.md)) |
| **Ratspeak** | v1.1.0 pre-release ([release notes](https://newreleases.io/project/github/ratspeak/Ratspeak/release/v1.1.0)) | RNS 1.6.0, LXMF 1.3.0, LXST 0.6.0 (stated) | Alpha. Adds "keep trying to send" for up to 24 h. Its own network of public nodes; a Rust Reticulum (`rsReticulum`) exists in the same organisation (feasibility Q-13) |
| **lxmd** (upstream) | in `lxmf` 1.3.1 | — | Reference propagation node, used in automated tests |

**[Assumption]** LXMF 1.3.0 and 1.3.1 interoperate: same major and minor version, a patch
release. **[Open]** Prove it with MS-14.

Interoperability risks:

| Risk | Mitigation |
|---|---|
| Stamp cost mismatch: Sideband 2.3 contacts may require a stamp; Ratspeak's defaults are unknown | Read the recipient's announced cost (LXMF does this automatically) and generate within a CPU budget (§8). Fail visibly ("needs a stamp the node could not make in time"), never silently |
| Ratchet enforcement on either side | Enable ratchets (LXMF default); do not *enforce* them on inbound in v0.3, or older senders would fail. Revisit in v0.4 |
| Rust implementation differences (`rsReticulum`) | Add to the test matrix once it ships a client. Public release gate RG-10 already covers this |
| Version drift (clients update often) | The matrix is re-run for every LXMF or RNS pin change, as with the RNS-pin process |

**Test plan.** Automated tests use real LXMF on isolated loopback networks: MeshBeacon's
messaging process, a scripted LXMF peer and upstream `lxmd`. A manual matrix covers Sideband
(desktop) and Ratspeak (desktop), each joined to an **isolated** test transport. They never touch
public infrastructure (rule 6). Every case is run in both directions: direct, opportunistic,
propagated, with stamps, offline recipient, and offline MeshBeacon.

## 5. Proposed architecture

### 5.1 Components

```text
 ┌───────────────────────── MeshBeacon app container ─────────────────────────┐
 │ core supervisor (existing)                                                  │
 │   ├── RNS node process (existing; transport, shared instance)               │
 │   └── messaging process (NEW, only when messaging is on; ADR 0008)          │
 │         LXMRouter (unmodified lxmf) ── RNS shared-instance client           │
 │         queue.db (SQLite, bounded; ADR 0011)   identity: messaging (ADR 0009)│
 │         optional propagation store (quota; ADR 0012, phase 3b)              │
 │   status API (existing, read-only, port 8100)                               │
 │   messaging API (NEW, port 8100, separate key and scope; ADR 0010)          │
 └──────────────────────────────▲──────────────────────────────────────────────┘
                                │ pinned TLS 1.3, internal network only
 ┌──────────────────────────────┴──── Home Assistant Core ─────────────────────┐
 │ meshbeacon integration: notify entities (per contact), event entities,      │
 │ meshbeacon.send_message action (response: message_id), repairs, panel tab   │
 │ "Messages" (only once messaging exists)                                     │
 └─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 Message flow

| Flow | Steps |
|---|---|
| **Send** (HA → contact) | (1) The integration calls `POST /api/v1/messages` with the contact ID, text and an **idempotency key**. (2) The messaging process stores it as `queued` and returns `message_id`. (3) The router sends it `DIRECT` (or opportunistically when small). (4) On `FAILED`, if a propagation node is configured, it is resubmitted once as `PROPAGATED`. (5) State changes are stored and exposed as receipts |
| **Receive** (contact → HA) | (1) The LXMF delivery callback fires. (2) Checks: signature validated, sender in contacts (or stamp-valid in "anyone" mode), size, rate. (3) The message is stored as `inbound/unacknowledged`. (4) The integration's long poll (`GET /api/v1/messages/inbound?after=<cursor>&wait=25`) receives it. (5) An HA event is fired. (6) The integration acknowledges the cursor and the app deletes the content (or keeps it for the retention period, if the user chose that) |
| **Fetch from node** | Every 15 minutes, and after each reconnection, the process asks its inbound propagation node for messages (`request_messages_from_propagation_node`). It does not fetch while the queue is full |

### 5.3 Offline cases

| Who is offline | Behaviour | Bound |
|---|---|---|
| Recipient | Direct attempts (LXMF: 5), then one resubmission as `PROPAGATED` if a node is configured; otherwise `failed` with the reason "recipient unreachable" | Pending outbound ≤ 7 days; then `expired` |
| MeshBeacon (app stopped, Pi off) | Senders' clients fall back to their propagation node; MeshBeacon fetches at start and every 15 minutes | Node's own expiry (LXMF 30 days) |
| Home Assistant | Inbound messages wait in the app until acknowledged; outbound requests cannot be made | Inbound store ≤ 500 messages or 2 MiB. When full, the **oldest unacknowledged** message is dropped and counted, never silently |
| Network partition during a send | The idempotency key makes the integration's retry safe; the app returns the original `message_id` | Keys remembered for 24 h |

### 5.4 Delivery receipts exposed to Home Assistant

| MeshBeacon state | From LXMF | User meaning |
|---|---|---|
| `queued` | before `handle_outbound` | Waiting to be sent |
| `sending` | `OUTBOUND`/`SENDING` | Trying to reach the recipient |
| `delivered` | `DELIVERED` | **The recipient's device confirmed it** |
| `stored_on_node` | `SENT` for `PROPAGATED` | Handed to a propagation node; the recipient will collect it later. **Not** confirmation |
| `sent_unconfirmed` | `SENT` for `OPPORTUNISTIC` without proof yet | Sent; no confirmation (yet) |
| `failed` | `FAILED`, or no route after fall-back | Not delivered; reason given in plain language |
| `rejected` | `REJECTED` (for example stamp refused) | The recipient refused it |
| `expired` | MeshBeacon's 7-day limit | Given up |

## 6. Home Assistant interface (ADR 0010)

### 6.1 The new write path

v0.2 is strictly read-only. v0.3 adds **sending**, which means Home Assistant can cause the node to
transmit. The controls:

- It is a separate option, **"Allow Home Assistant to send messages"**. It is off by default and
  separate from the receive option.
- It uses a **separate messaging key**, rotated at every start and delivered through the same
  Supervisor discovery. The read-only status key cannot send.
- The endpoints are `POST /api/v1/messages` and `GET /api/v1/messages/{id}` and
  `/inbound` (long poll). They are served only while messaging is on, on the same pinned TLS
  listener and with the same connection limits.
- Recipients can only be **contact IDs** from the app's allow-list, never raw LXMF addresses
  from Home Assistant. A compromised automation therefore cannot message arbitrary addresses.
- Sends are rate-limited: 10 a minute and 100 a day by default, plus per-contact limits.
- **No other control.** There is no endpoint to change options, identities, contacts, the
  propagation node or Reticulum.

### 6.2 Entities, actions and events

| HA element | Purpose |
|---|---|
| `notify.meshbeacon_<contact>` (NotifyEntity) | Standard "send a notification" target per contact; works with existing automations and scripts |
| Action `meshbeacon.send_message` (contact, message, title) | Returns `message_id` (action response), for automations that wait for a receipt |
| `event.meshbeacon_message_received` | Event types `message`, `unverified_dropped` (count only). Attributes: contact ID, contact name, `message_id`, time, `content` (**not recorded**, §6.3) |
| `event.meshbeacon_message_status` | Event types `delivered`, `stored_on_node`, `failed`, `rejected`, `expired`, with `message_id` and reason |
| Sensors | Queue length, unacknowledged inbound, messages dropped (rate, size, unknown sender), propagation node reachable (diagnostic) |
| Repairs | "Messaging identity problem", "Inbound store full", "Propagation node unreachable for 24 h" |
| Blueprint (YAML, docs only) | "MeshBeacon message → mobile notification with Reply". It uses the companion app's actionable notifications and sends the reply back through `notify.meshbeacon_<contact>`. **Default text: 'New MeshBeacon message from <contact>', without the content** (§6.3) |
| Built-in interface | **Revised for the out-of-the-box principle and [ADR 0013](../adr/0013-built-in-interface-ingress.md) (proposed).** The dedicated interface moves into the app, served through Ingress, which is **read-only** because the Supervisor → app hop is plain HTTP (T62). A **Messages** tab, shown only when messaging is on, can therefore *display* conversations and receipts out of the box. **Composing a message is not offered through Ingress** until an integrity-protected path exists; sending stays with HA (notify entities and the action, ADR 0010) when the optional integration is installed. **[Open] Q-47:** how to offer out-of-the-box sending without the integration and without weakening T62. In-page tokens or encryption cannot help: they travel over the same unprotected hop (option H, rejected). See [secure interface options](secure-interface-options.md). Needs review |

### 6.3 Message content and privacy inside Home Assistant

| Where content could leak | Default decision |
|---|---|
| Recorder (event entity attributes) | `content` and `title` are in `_unrecorded_attributes` **[Verified: HA supports it, `helpers/entity.py`]**, so they are never written to the database |
| HA event bus history | No custom bus event with content; automations use the event entity's trigger |
| Logs and diagnostics | Never log content, titles or addresses. Diagnostics give counts only (tested as T29 is) |
| Mobile push (Apple/Google relays) | The blueprint omits the content by default, and its description says why. The user can choose to include it |
| HA backups | Content is not in HA's database. The app keeps unacknowledged inbound messages and the outbound queue in `/data/messaging/`, which is in the **app's** backup; document this |
| The panel | Messages are shown from the integration's memory (the last 50 per contact) and fetched on demand from the app; there is no browser storage |

## 7. Identity, encryption, authentication and metadata

| Topic | Proposal |
|---|---|
| **Separation** (ADR 0009) | A **separate messaging identity**, distinct from the transport identity: its own file (`/data/messaging/identity`, 0600), its own validation before start (rule 13), its own backup and restore path. A compromised or replaced messaging identity does not change the node's transport identity, and the reverse |
| Announces | The messaging destination is announced at start, then every 6 hours (configurable, minimum 1 h). **Display name: empty by default** (an announce is public), user-settable |
| **Encryption** | End-to-end by LXMF/RNS (Curve25519 + AES-256; ratchets on by default). No custom cryptography (rule 2) |
| **Authentication of senders** | Accept only `signature_validated` messages. `SOURCE_UNKNOWN` (sender identity not yet known): request the identity once, hold the message ≤ 10 minutes, then drop and count it |
| **Contacts** | Allow-list in the app's options (name + LXMF address). Contacts are the only senders accepted by default and the only recipients Home Assistant can address |
| **Metadata** | Unavoidable and documented: propagation nodes learn the recipient hash, size and timing; the network sees announces and link timing; the transport identity and messaging address are announced from the same node, so an observer can **correlate** them. **[Assumption]** separation protects against key compromise, not against network-level correlation. No location, telemetry or icon fields are sent |
| Logging | Addresses are redacted like other hashes; content and titles are never logged |

## 8. Spam, limits and resource use

### 8.1 Spam prevention and limits (defaults, all bounded)

| Control | Default |
|---|---|
| Inbound mode | **Contacts only.** "Anyone" mode requires an inbound stamp cost (default 8 **[Assumption]**, tuned in testing) |
| Tickets | Issued to contacts so they skip stamps (LXMF tickets, 21-day expiry) |
| Size | Inbound content ≤ 8 KiB; LXMF `delivery_limit` set to 16 KB; fields other than title and content ignored |
| Rates | Inbound ≤ 30 a minute overall and ≤ 10 a minute per sender; above that, dropped and counted |
| Storage | Inbound unacknowledged ≤ 500 messages and 2 MiB; outbound pending ≤ 200 messages; retention of acknowledged content: 0 days (default) to 30 days; `queue.db` hard cap 16 MiB |
| Ignore list | `ignore_destination` for senders the user blocks (from the panel, later) |
| Propagation node (phase 3b) | `message_storage_limit` default 64 MiB (maximum 1 GiB, and never more than 25 % of free space); static peers only; auto-peering off; `max_peers` 4 |

### 8.2 Resource budgets on the reference Raspberry Pi (release gates)

| Resource | Budget | How measured |
|---|---|---|
| Memory, messaging off | **No change** from v0.2 (the process is not started) | `Status:` line, step B6 |
| Memory, messaging on (idle) | ≤ **+40 MiB**; whole app ≤ **160 MiB** RSS + swap | 1-hour idle reading |
| Memory, propagation node on | ≤ +24 MiB above messaging, plus the store on disk | 1-hour reading with a full quota |
| CPU, idle | ≤ 0.5 % of one core added (announces, fetches, jobs) | 1-hour average |
| CPU, stamp generation | Per message ≤ 30 s at the recipient's announced cost; otherwise `failed: stamp too costly` | Measured on the Pi at costs 8, 12 and 16 |
| Disk | Bounded by §8.1; never more than 25 % of free space | Fill test |
| Storage writes | SQLite WAL, `synchronous=NORMAL`; ≤ 1 write a second sustained (SD-card wear) | Write-counting test |

**[Open]** The cost of a second RNS client process and of LXStamper on a Pi 4 is not measured.
These are the first measurements of the prototype phase, and they decide whether ADR 0008's
separate process holds (§10).

## 9. Threat modelling and failure isolation

New trust boundaries:
- **B9: remote LXMF senders.** Content and timing are attacker-controlled. Messages flow into
  Home Assistant automations.
- **B10: Home Assistant → app messaging API.** The first write path.

The threats are listed as T43–T58 in the [threat model](../security/threat-model.md) (proposed,
v0.3). The most important design consequence:

> **A received message must never become a command.** Automations triggered by message content
> are remote control by another name (v0.6's highest-risk area). v0.3 delivers content as untrusted
> text, adds no "commands" helper, and documents that automations should match only on the
> contact, not on content. The blueprint does not run actions from content.

Failure isolation (ADR 0008):

| Failure | Effect, by design |
|---|---|
| Messaging process crashes or hangs | Restarted with bounded back-off (as ADR 0005). **Transport and the status API are unaffected**. After 5 failures in 30 minutes, messaging pauses and raises a repair issue |
| `queue.db` corrupt | The file is moved to `queue.db.corrupt-<time>`, a fresh queue is started, and a repair issue lists how many messages could not be recovered |
| Messaging identity invalid | Messaging refuses to start (rule 13). Transport continues |
| Disk full | New inbound refused and counted; outbound refused with a clear error; nothing else stops |
| HA unreachable | Inbound waits within bounds (§5.3); nothing affects RNS |
| Stamp generation runs long | It runs in the messaging process with a CPU time limit and `nice`, and never blocks the core |

## 10. Options considered (summary; detail in the ADRs)

| Decision | Chosen | Alternatives rejected | Why |
|---|---|---|---|
| Where LXMF runs (ADR 0008) | **Separate supervised process**, an RNS shared-instance client | Inside the RNS node process (less memory, but a messaging fault would take transport down); upstream `lxmd` as-is (it is a propagation daemon, not a delivery client with an API) | Failure isolation and a clean "off = zero cost" |
| Identity (ADR 0009) | **Separate messaging identity** | Reuse the transport identity (one key to protect, but no separation) | Compromise and replacement independence |
| HA interface (ADR 0010) | **Pinned-TLS API, separate key, contact IDs only, long poll** | Ingress; the app calling HA (`homeassistant_api` permission); MQTT (an extra broker and an extra trust boundary) | No new app permission, the same transport as v0.2, push-like delivery without websockets |
| Queue (ADR 0011) | **SQLite in `/data/messaging/`** | JSON files (non-atomic, slow at scale); relying on LXMF's memory queue (lost at restart) | Atomic, bounded, standard library |
| Propagation node (ADR 0012) | **Optional, off, static peers, quota, phase 3b** | On by default; public auto-peering | Resource use and exposure on a home Pi |
